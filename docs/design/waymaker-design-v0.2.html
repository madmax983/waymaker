Waymaker: durable workflows for firmware

A tiny Rust record-and-replay engine that lets deterministic workflows survive brownouts, watchdog resets, and power loss—without pretending an MCU is a server.

The machine may die. The workflow does not get to pretend the committed past did not happen.

01 Summary

Waymaker is a firmware-first durable workflow engine for Rust. A workflow is re-created from its beginning after reboot and deterministically replayed through an ordered journal. Completed effects return their recorded results; the first unresolved effect becomes the next piece of work.

The semantic kernel does not persist Rust stacks, futures, heap graphs, or executor state. It persists only a compact history of effect boundaries and outcomes. An optional Embassy adapter turns those boundaries into familiar ctx.activity(...).await and timer APIs.

Design center Waymaker does not make arbitrary Rust futures durable. It makes the observable path through a deterministic workflow durable.

Streaming replay

History is consumed sequentially from flash with one caller-owned scratch page. No in-RAM journal or index is required.

Durable outbox

Effect intent is committed before physical execution. Results are committed before the workflow may observe them.

Bounded by design

Payloads, history, buffers, identifiers, and retries all have explicit limits and explicit exhaustion behavior.

02 Settled design decisions

  1. The kernel is no_std, no_alloc, and dependency-free. Serialization, logging, executors, and hardware drivers live above it.
  2. Replay is sequential. A cursor advances through history in workflow order; the engine never requires Journal::get(id) or an in-memory event index.
  3. Physical effects happen only after durable intent. The schedule record crosses a durability barrier before dispatch.
  4. History records use numeric kinds and borrowed bytes. Strings, Vec, Serde, and Postcard are optional user-facing conveniences, not wire-format requirements.
  5. Normal async syntax is an adapter. waymaker-embassy supplies the ergonomic façade; the persistence protocol does not depend on Embassy or Future.
  6. Arbitrary suspended futures are not snapshotted. Bounded-history reclamation occurs at an explicit continue_as_new boundary.
  7. Two flash banks provide atomic run replacement. A new run becomes authoritative only after its payload and generation seal are durable.
  8. Durable timers require durable time. A resettable monotonic clock cannot claim that time elapsed while power was absent.

03 Goals and non-goals

Goals

  • Run on Cortex-M0+ class devices.
  • Require no heap in the runtime.
  • Recover to a legal committed history prefix after power loss at any write boundary.
  • Offer deterministic activity, timer, completion, and failure boundaries.
  • Integrate cleanly with Embassy without replacing its executor.
  • Make RAM, code flash, data flash, and write amplification measurable.
  • Permit hardware-specific storage beneath a narrow protocol.

Non-goals for v0.x

  • Persist arbitrary stacks or suspended futures.
  • Exactly-once physical side effects.
  • SQLite, filesystems, networking, or host databases in the firmware runtime.
  • Distributed consensus or multi-writer histories.
  • Dynamic workflow loading or string-addressed activity registries.
  • Unbounded payloads, histories, mailboxes, or retry queues.
  • Compatibility with Temporal's wire protocols or server APIs.

06 Workflow model

A workflow is a deterministic function from recorded input and recorded effect results to the next effect request or terminal outcome.

pub async fn ota_update(
    ctx: &mut Ctx<'_>,
    input: OtaInput,
) -> Result<(), OtaError> {
    // Small durable value: a handle, not the image bytes.
    let image: ImageSlot = ctx
        .activity(ActivityKind::DOWNLOAD, input.url_bytes())
        .await?;

    ctx.activity(ActivityKind::VERIFY_SIGNATURE, image.as_bytes()).await?;
    ctx.activity(ActivityKind::FLASH_IMAGE, image.as_bytes()).await?;

    ctx.complete(&[]).await
}

Cold-start replay

  1. Recover the active bank and its committed record prefix.
  2. Decode the run input into caller-owned storage.
  3. Create a fresh workflow future and replay cursor.
  4. Poll the workflow from its beginning.
  5. Each effect consumes the matching history records or identifies the first unresolved effect.
  6. Stop at pending work or a terminal record.

The future itself is disposable. Recreating it is the recovery mechanism. Within one boot, the Embassy adapter may retain and poll it normally; after reset, replay reconstructs its observable state.

Explicit kernel boundary

pub enum Resolve<'a> {
    // Completion already exists in committed history.
    Replayed { result: &'a [u8] },

    // Intent is committed; dispatch or redeliver using this stable ID.
    Dispatch { id: EffectId },

    // Waiting for a completion or external wakeup.
    Pending { id: EffectId },
}

pub struct EffectRequest<'a> {
    pub kind: ActivityKind,
    pub input: &'a [u8],
}

07 Durable effect protocol

No exactly-once physical promise Power can fail after the activity changes the world but before its completion is committed. Waymaker will redeliver the same stable effect ID. Exactly-once behavior requires an idempotent activity or a downstream system that deduplicates that ID.

Compact effect identity

pub struct RunId(pub u64);
pub struct EffectSeq(pub u32);

// Unique on a device when combined; only EffectSeq is repeated
// in every record because RunId lives in the bank header.
pub struct EffectId {
    pub run: RunId,
    pub seq: EffectSeq,
}

Effect sequences never reset within a run. Wraparound is a terminal IdExhausted condition, not silent reuse.

08 Replay and determinism

Waymaker consumes history in the same order the workflow encounters effect boundaries. That makes replay constant-memory and avoids random reads or lookup tables.

Next history stateWorkflow callEngine action
Matching schedule + completionSame effect kind and input digestReturn the recorded result and advance the cursor.
Matching schedule onlySame effect kind and input digestRedeliver using the existing effect ID.
End of historyNew effect callAppend and commit a schedule record, then dispatch.
Different kind, digest, or sequenceReplay divergenceStop with NondeterministicWorkflow; never guess.
Terminal workflow recordFurther executionReturn stored completion/failure without polling further.

Determinism is a contract

Workflow code must not read hardware registers, ambient time, randomness, mutable statics, network state, or nondeterministic iteration order directly. Those values enter through recorded effects. The type system cannot prove this property for arbitrary Rust; Waymaker detects divergence at effect boundaries and later tooling may lint suspicious APIs.

Workflow versioning

Every run pins a workflow_kind, workflow_version, and input schema in its bank header. v0.1 deliberately chooses the smallest safe upgrade rule:

  • Existing runs must continue under compatible code for their recorded version.
  • A firmware image that cannot replay the recorded version returns IncompatibleWorkflow.
  • Code changes that add, remove, or reorder effects require a new version or an explicit recorded version gate.
  • Source-location hashes are not stable identity; call-order sequencing remains authoritative.

09 Journal and wire format

The wire format is handwritten, fixed-endian, self-delimiting, and independent of Rust layout. User payload bytes are opaque to the kernel.

RecordFrame
  magic          u16 LE
  format_version u8
  record_kind    u8
  effect_seq     u32 LE
  payload_len    u16 LE
  header_crc     u16 LE
  payload        [payload_len]
  payload_crc    u32 LE
  commit_seal    storage-program unit

The exact header size may change during implementation, but these properties may not:

  • All lengths are validated against caller buffers and bank bounds before reading.
  • Unknown record kinds are skippable only when the format version permits forward compatibility.
  • A payload barrier completes before the commit seal is programmed; a second barrier makes that seal durable.
  • Recovery stops at the first unsealed, malformed, out-of-sequence, or integrity-failed frame.
  • CRC detects accidental corruption and torn writes; it is not authentication.
  • Records are padded to the device's program alignment without interpreting stale tail bytes.

10 Two-bank lifecycle

Waymaker owns two fixed storage banks, usually one erase block each. The bank with the highest valid generation seal is authoritative. Its journal is then scanned to the last valid committed record.

continue_as_new

A normal async workflow cannot serialize its hidden suspension state. Waymaker therefore does not disguise storage maintenance as a magical snapshot. The workflow explicitly supplies the bounded input for its next run.

  1. Stop accepting new effects for the current run.
  2. Erase the inactive bank.
  3. Write the new bank header, new RunId, workflow version, and next-run input.
  4. Barrier: the new bank payload becomes durable.
  5. Write the higher-generation bank seal.
  6. Barrier: the new bank becomes authoritative.
  7. Return success to the workflow adapter and lazily erase the old bank.

A crash before step 5 recovers the old run. A crash after step 6 recovers the new run. Recovery never combines their footprints.

Capacity is explicit Waymaker reserves enough tail space for a terminal record or continue_as_new. Ordinary effect scheduling fails early with HistoryNearCapacity; the runtime never overwrites committed history to make room.

11 Time and timers

A monotonic MCU timer usually returns to zero after reset. It cannot reveal how long the device was unpowered. Waymaker therefore exposes timer semantics that match the hardware's actual clock capability.

pub enum TimerSpec {
    // Begins again after a reboot when no persistent time source exists.
    AfterBoot { ticks: u64 },

    // Survives power-off only with an RTC or externally restored epoch.
    AtPersistentTime { instant: u64 },
}

pub trait PersistentClock {
    type Error;
    fn now(&mut self) -> Result<u64, Self::Error>;
}

The Embassy adapter may also offer ordinary in-boot sleep, but documentation must not call it power-loss-durable. A persistent timer record includes its clock kind so recovery cannot silently reinterpret one policy as another.

12 Storage interface

The flash adapter needs geometry and ordering, not a fake filesystem. It can adapt embedded-storage implementations without making that crate a kernel dependency.

pub struct Geometry {
    pub capacity: u32,
    pub erase_size: u32,
    pub program_size: u16,
    pub read_size: u16,
}

pub trait StableStorage {
    type Error;

    fn geometry(&self) -> Geometry;
    fn read(&mut self, offset: u32, dst: &mut [u8]) -> Result<(), Self::Error>;
    fn program(&mut self, offset: u32, src: &[u8]) -> Result<(), Self::Error>;
    fn erase(&mut self, offset: u32, len: u32) -> Result<(), Self::Error>;
    fn barrier(&mut self) -> Result<(), Self::Error>;
}

Required storage contract

  • program and erase may fail or be interrupted at any supported unit.
  • After barrier returns, all earlier successful mutations survive reset.
  • No later mutation may become durable before mutations ordered by a completed barrier.
  • The adapter validates erase/program alignment before touching media.
  • Flash-specific one-way bit programming rules remain the driver's responsibility.

Disabling interrupts is not part of the durability proof. A blocking internal-flash implementation may need to do so for hardware reasons, but the protocol is expressed entirely in durable ordering and recoverable bytes.

Borrowed kernel records

    RunStarted {

Embassy-facing façade

impl<'a, D, J> Ctx<'a, D, J>
where
    D: ActivityDispatcher,
    J: Journal,
{
    pub fn activity<'b, T: Decode>(
        &'b mut self,
        kind: ActivityKind,
        input: &'b [u8],
    ) -> ActivityFuture<'b, T, D, J>;

    pub fn timer<'b>(
        &'b mut self,
        spec: TimerSpec,
    ) -> TimerFuture<'b, D, J>;

    pub fn continue_as_new<'b>(
        &'b mut self,
        input: &'b [u8],
    ) -> ContinueFuture<'b, J>;
}

Decode is a tiny adapter trait operating over borrowed bytes and caller-owned output. A Postcard/Serde implementation is optional; the core does not require a particular codec.

Activity dispatcher

pub trait ActivityDispatcher {
    type Error;

    async fn dispatch(
        &mut self,
        id: EffectId,
        kind: ActivityKind,
        input: &[u8],
        output: &mut [u8],
    ) -> Result<usize, Self::Error>;
}

Activity names are compile-time metadata for logs and diagnostics. The runtime dispatch path uses numeric kinds and does not store names in every record.

Guarantees

  • Prefix safety: recovery exposes only a legal prefix of committed records.
  • Acknowledged durability: any record acknowledged after its barrier is recovered after reset.
  • Durable intent: no Waymaker-dispatched effect lacks a recoverable schedule record.
  • Stable redelivery: retries and reboot redelivery reuse the original effect identity.
  • Bounded decoding: malformed storage cannot cause out-of-bounds reads or allocation.

15 Testing and verification

The persistence protocol is small enough to test exhaustively at its real semantic boundaries. Crash testing is part of the design, not a post-MVP hardening phase.

Model and property tests

  • Random record sequences and storage geometries.
  • Torn writes at every byte/program unit.
  • Power loss before and after every barrier.
  • CRC corruption, stale tails, and malformed lengths.
  • Sequence wrap and capacity boundaries.
  • Bank generation selection under partial swaps.

Firmware gates

  • Build on thumbv6m-none-eabi with no default features.
  • Link example firmware and record section deltas.
  • Measure generated workflow future sizes.
  • Run hardware power-cut loops against real NOR flash.
  • Track erase counts and per-effect write amplification.
  • Test watchdog resets during schedule, dispatch, and completion.

Core property oracle

// For every possible crash point:
recovered_history.is_prefix_of(committed_history)
    && acknowledged_records.all(|r| recovered_history.contains(r))
    && dispatched_effects.all(|e| recovered_history.has_schedule(e.id))
    && recovered_banks.count_authoritative() == 1

The model distinguishes records that were merely attempted, records that may have become durable before acknowledgment, and records whose barrier returned. Recovery may include an unacknowledged complete record, but it may never lose an acknowledged one.
